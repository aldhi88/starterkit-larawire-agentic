# Optional CMS

## Installation and ownership

- CMS is an optional, package-maintained capability. The installation wizard always creates the selected first dashboard App and a root-domain landing page. Selecting CMS additionally creates the `cms` App; declining CMS publishes no CMS registry, route shim, migration, or tables.
- `cms` is reserved for the optional CMS and `api` for the shared API gateway. Never replace an existing custom App that occupies either CMS source path. Existing installations add CMS locally with `starter:cms --dry-run`, then `starter:cms`; production receives the reviewed host source and uses `starter:deploy`.
- CMS runtime PHP, theme views, and tests belong to the canonical package. Host-owned activation files are `config/apps/cms.php`, `routes/apps/cms.php`, and `database/migrations/apps/cms/`. The migration source is maintained under `installer/templates/cms/`; it is not loaded from the core migration path.
- All CMS tables use the explicitly approved `cms_` prefix. Content uses fixed `post`, `page`, and `card` kinds in `cms_contents`; taxonomy uses the matching kinds in `cms_categories`. Do not introduce tenant/client IDs or duplicate authentication, roles, or company settings.
- CMS files are additive. Activation validates every target before publication, preserves managed host customizations, and removes only newly created source after failure. Applied additive migrations are retained for a safe retry; activation never resets the application database.
- `starter:reset` includes CMS App source, tables, and private CMS uploads in its destructive scope and warning. Installation snapshots include private uploads so a pre-mutation failure can restore them.

## Dashboard and access

- The seven authorization modules match the requested editorial groups: `dashboard`, `posts`, `pages`, `cards`, `media`, `menus`, and `comments`. Category pages share their content module; galleries share `media`. Each module owns all its route names and its complete menu subtree.
- Navigation is: Dashboard → Beranda; Konten → Semua Postingan, Post Baru, Kategori Post; Halaman → Semua Halaman, Halaman Baru, Kategori Halaman; Card → Semua Card, Card Baru, Kategori Card; Media → Pustaka Media, Galeri; Menu → Semua Menu, Kategori Menu; Komentar.
- Create shortcuts belong to the same module as the list and edit pages. They do not add per-button permissions. Apply the standard authenticated/active/password-change/lock/module middleware and authorize every server-side action.
- CMS is available on `cms.<APP_DOMAIN>`. Root-domain helper routes use `starter.cms.*` names so they never enter App module/menu synchronization. The default landing links to the static usage documentation only when CMS is enabled.
- Apply the shared audit, actor ownership, PowerGrid filters/pagination, archive/restore/permanent-delete, selected/by-filter actions, and theme dialog contracts. CMS UI must be implemented and verified in every supported theme.
- Tabler post-table quick actions support publish-now, draft, and category replacement through a compact collapsible category tree (no operation selector) for one row, selected IDs, or all active filtered results (limit 1,000). Preview count/scope and scheduled-post impact before applying. Preserve unrelated post fields, existing dates for already-published posts, and unrelated category branches during checkbox interaction. Category branches start collapsed for bulk actions, expand to existing selections when editing, and show matching ancestry during search. Disclosure buttons, parent labels, and parent rows expand or collapse; only a checkbox click changes selection, and collapsing never clears selections. Bulk selection starts empty; row editing preselects current assignments. Saving empty clears categories. In Tabler post forms and table dialogs, checking a node selects its descendants and ancestors; unchecking a node clears its descendants while preserving other branches, and automatically clears ancestors when their last selected child is removed. Server normalization includes available ancestors without selecting siblings of a selected child. Legacy parent-only assignments initialize as full branch selections in the editor; opening or cancelling does not write these changes. Validate authorization, exact filtered IDs and record/category snapshots again at apply; reject stale/archived/wrong-kind records atomically. Log actor-bound before/after state and refresh PowerGrid without a reload. Category display/filtering must include all assigned categories. Other theme presentation remains unchanged until requested.
- Taxonomy management uses a compact add/edit form beside its PowerGrid list, with the form first and the list second. Post categories may choose a parent category to create a hierarchy; other taxonomy forms remain name-only. The Tabler post-category table defaults to parent-before-child hierarchy order, indents descendants, and retains the full ancestry path when searching or paginating. Category names are editable; existing mapping codes, status, and position are preserved. Tabler post-category rows can be dragged directly in PowerGrid using the locally bundled SortableJS; Alt+Up/Down on the row grip is the keyboard alternative. Dropping a row saves automatically without a separate ordering dialog. Only siblings move relative to one another; filtered/paginated moves preserve unseen siblings and descendants. Dragging is available in the active hierarchy sort, with a small hierarchy-reset link when another column sort is selected. Reordering preserves parent relationships, moves a parent with its descendants, saves sibling positions atomically with actor-bound audit, and rejects stale category snapshots. Create/edit and ordering saves refresh the mounted PowerGrid without a page reload.
- Pustaka Media provides a multiple-file upload/drop area above a searchable, paginated visual media library. Galeri opens the same complete library in browse mode. Existing album data and developer reader contracts remain available through the secondary album management routes. Visual media cards are not tabular data; any table view continues to use PowerGrid.
- Content authoring uses the locally served Quill editor and CMS media selection/upload. Menu items support visual drag-and-drop order and nesting, with accessible button alternatives and the same validated three-level hierarchy.

## Content and public integration

- Frontend composition is owned by the programmer using the starter kit. CMS does not build a public website or prescribe page components, templates, or section layout. Preserve the existing default landing.
- One Card is one reusable content entry, such as a carousel slide, client logo, service, or greeting. A category code identifies a programmer-selected content group. Its name may change independently; code changes affect frontend mappings and must be deliberate.
- Card fields are optional except its internal management name. A frontend reads only the fields it needs: title/subtitle/slug/excerpt/body, image/thumbnail/logo, link label/URL, position, and publication state. A media-only Card must not require a visible title or article body.
- Post authoring requires a title and derives the retained legacy management name from it. Posts have no manual ordering input; existing position values are preserved but public post lists use publication time descending with a stable descending ID tie-breaker. A post may have multiple hierarchical categories; existing single-category data is migrated into the post-category relation. A new post starts as a draft with the current Asia/Jakarta publication date/time. The Tabler post form uses an Indonesian calendar/time picker with a locale-independent DD/MM/YYYY HH:mm value, 24-hour WIB time, and server-side validation; other theme date inputs and CMS table dates display WIB. Input converts to the host application timezone for storage and scheduling. Publishing with an empty date uses the current server time. Page and Card fields and ordering remain unchanged.
- Public readers must filter archived, draft, future-scheduled, inactive-category, and inactive-media records before pagination, counts, lookup, or nested output. Do not advise frontend programmers to query unrestricted CMS models for public rendering.
- Public rendering escapes user text. HTML/rich-content rendering requires an explicitly safe renderer; raw database content must never be printed unescaped. URLs use validated safe schemes, and frontend links retain the necessary target/rel protections.
- Rich HTML is cleaned server-side with an explicit allowlist. The renderer supports existing Markdown and new HTML records. Only sanitizer-generated, bounded content formatting may use inline styles; application/theme layout styling still belongs to its owning stylesheet. Embedded images refer to active CMS media and retain relational lifecycle protection; stored references are portable across deployment domains.
- Editor image resizing persists numeric HTML width and height attributes from 1 to 10,000 pixels; the safe renderer retains valid dimensions and discards malformed or out-of-range dimensions. Responsive frontend layout remains programmer-owned.
- Media are safe, validated images or PDF files on the private local disk. Public delivery uses a non-sequential public identifier, active-record checks, MIME restrictions, and the package delivery route. Never publish private filesystem paths or serve executable uploads.
- Public comments concern published posts and enter moderation before publication. A developer integrates comment submission into their own frontend with CSRF, rate limits, validation, and spam controls; CMS does not silently expose an unauthenticated write API.
- Keep the static usage page and README examples synchronized with the tested reader contract, including stable category codes, pagination, publication rules, menu nesting, and media URLs. Documentation must never enumerate real private/draft content.
